## 筛选条件的取值语义

三个筛选条件 `hours`、`minFileSizeMB`、`maxFilesPerShare` 都可用在全局，也可写在 `shareUrls` 的每一项里覆盖全局值。合并方式是 `??`（nullish），也就是**只认 `undefined` / `null` 为「未配置」**，写 `0` 一律视为显式覆盖：

- `minFileSizeMB: 0`、`maxFilesPerShare: 0` = 不限制（覆盖掉全局的较小限制）
- `hours: 0` = 只转存「此刻及之后更新」的文件，**实际等于什么都转存不了**，通常不是你想要的结果；只想沿用全局窗口就把该字段省略

### 「多久内更新」的单位写法

`hours` 除纯数字（按小时）外，还支持带单位：

| 写法 | 含义 | 折算小时 |
| --- | --- | --- |
| `30m` | 30 分钟 | 0.5 |
| `12h` / `12hr` | 12 小时 | 12 |
| `1d` | 1 天 | 24 |
| `1w` | 1 周（7 天） | 168 |
| `1mo` | 1 个月（按 30 天计） | 720 |
| `1y` | 1 年（按 365 天计） | 8760 |

- 支持小数与混合大小写：`1.5d`、`0.5w`、`2D`、`"1 d"`（含空格）均可
- 纯数字仍按**小时**解释，因此旧的 `"hours": 24` 配置不受影响
- ⚠️ **`m` 表示分钟，月请用 `mo`**：`30m` 是 30 分钟，`30mo` 才是 30 个月
- `mo` 与 `y` 是固定折算（30 天 / 365 天），不按自然月或闰年计算
- 无法识别的写法（如 `1x`）会回退到默认值 48 小时，并在日志中以 `⚠ hours 取值无法识别` 提示；网页保存时会直接拒绝
- 历史字段 `days` 保持原有语义：`days: 0` 视为未配置并回退默认值（不会变成「0 天窗口」）

日志中会以可读形式回显实际窗口，例如 `时间范围: 最近 1 天更新`。

### 配置示例

```json
{
  "cookie": "你的夸克Cookie字符串",
  "hours": 3,
  "minFileSizeMB": 100,
  "maxFilesPerShare": 3,
  "targetDirName": "来自：分享",
  "shareUrls": [
    {
      "url": "https://pan.quark.cn/s/xxxxxxxx",
      "password": "提取码",
      "tip": "遮天-",
      "hours": 6,
      "minFileSizeMB": 200,
      "maxFilesPerShare": 2
    },
    { "url": "https://pan.quark.cn/s/yyyyyyyy", "tip": "斗破苍穹-" },
    {
      "url": ["https://pan.quark.cn/s/main1", "https://pan.quark.cn/s/backup1"],
      "tip": "备用链接示例",
      "maxFilesPerShare": 0
    }
  ]
}
```

上例第三个分享显式写 `"maxFilesPerShare": 0`，表示该链接不受全局 `maxFilesPerShare: 3` 限制；省略该字段则继承全局值。

按单位写法表达长短不同的窗口：

```json
{
  "hours": "1d",
  "shareUrls": [
    { "url": "https://pan.quark.cn/s/xxxx", "tip": "日更-", "hours": "12h" },
    { "url": "https://pan.quark.cn/s/yyyy", "tip": "合集-", "hours": "1y" }
  ]
}
```

## 转存目标

### 多级路径的解析规则

`targetDirName` 支持多级路径，例如 `转存/来自：分享`：按 `/` 拆分后逐级查找，不存在的层级会在上一级下自动创建。规则与限制：

- 每级都以上一级的 fid 作为父目录，因此只支持**从根目录往下**的相对层级
- 空段（开头、结尾、重复的 `/`）一律忽略：`/a//b/` 等价于 `a/b`
- `.` 与 `..` **没有特殊含义**，按普通文件夹名字处理
- 某级创建后若拿不到 fid，会直接报错中断，而不是带着错误的父目录继续往下建
- **不设置 `targetDirName`（也没设 `targetDirFid`）时会直接转存到网盘根目录** —— 代码里没有「默认文件夹名」这回事，示例配置里给的 `来自：分享` 只是模板值

日志会逐级回显：

```
   查找目标文件夹: "转存/来自：分享"...
   ✓ 转存 已存在，fid: ...
   来自：分享 不存在，正在创建...
   ✓ 来自：分享 已创建，fid: ...
```

### targetDirFid 与界面提示

`targetDirFid` 的优先级**高于** `targetDirName`，且不在网页界面上出现（属高级选项，直接改 `config.json`）。因为优先级更高，只要磁盘上设了它，网页「配置」页就会显示一条提示并带出该值 —— 否则用户改了「目标文件夹名」却看不出效果，属静默失败。

它仍会被保留：网页保存配置时，这三个不在界面出现的全局字段按下面的规则处理 —— 字符串原样保留，数字转成字符串（例如手写配置里未加引号的 `"password": 1234`），其余（`null`、布尔、对象）直接丢弃，避免后端校验拒掉整个保存。

## 去重与重命名

去重比对用的是**「文件名 + 文件大小」**，因此同名但大小不同会被视为另一份内容并照常转存。

此时若「前缀 + 原名」已被占用（例如上次已存过同名文件），不会覆盖也不会丢下不加前缀的文件，而是改用带序号的名字（`择日飞升-11 4K HDR (2).mp4`），两份都保留，日志中会有 `已存在，加序号避免覆盖` 提示。序号名会顺延到第一个空位；万一连序号名都被占满（默认试到 999），则放弃本次重命名并在日志中说明 —— 因为改名到一个已存在的文件上可能覆盖别人的文件，宁可保留原名。

另外，若分享里的文件**本身就带这个前缀**（例如 `tip` 与剧集名相同，文件已经叫 `遮天-01.mp4`），不会再叠加成 `遮天-遮天-01.mp4`，而是跳过重命名。

同名集数的多个版本（如 4K 与 1080p）会自动去重，按画质评分保留最高清的那份；同画质则保留体积更大的。

## 下载

`.downloaded.json` 按「文件名 + 大小」记录已下载的文件，下次运行自动跳过，防止重复下载；`--force-download` 可忽略记录全部重下。

### 完整性校验

每个文件下载完成后都会核对**实际写入的字节数**，比对三项：响应是否完整收完、`Content-Length` 是否吻合、列表里声明的文件大小是否吻合。任一不符即判定失败：删除半成品、**不写入** `.downloaded.json`，下次运行自动重试。

这项校验是必要的：仅凭写入流的 `finish` 事件判断成功并不够 —— 上游提前结束（尤其服务端用 chunked、不带 `Content-Length` 时）也会触发 `finish`，于是被截断的文件会被当成下载成功并记入记录，**从此被永久跳过、不会再重下**，表现为「网盘里 3G，本地只有 300M」且不会自愈。

同时，下载先写 `.part` 临时文件，校验通过后才改名为正式文件。好处有两个：半成品不会冒充成品；重新下载失败时也不会把上一次的好文件毁掉。

### 自愈

跳过判定不再只看记录：对已记录的文件还会核对本地副本是否**存在且大小相符**，不符则重新下载。因此历史上被截断的文件会在下次运行时自动修复，日志中会给出：

```
⚠ 有 1 个文件本地副本缺失或大小不符，将重新下载
```

## 定时调度

`syncCron` 与 `alistCron` 都支持**字符串或数组**（数组即多个时间点）。`syncCron` 与 `alistCron` 用的是两把不同的任务锁，**可以并发**。

### 为什么推荐 downloadAfterSync

「同步 11:00 / 下载 11:05」这种写法是靠猜同步要跑多久 —— 同步一旦超过这个间隔，下载就会在同步还没结束时去列目录，可能漏文件或拿到还没转存完的内容。

开启 `downloadAfterSync` 后，同步任务跑完会**紧接着**执行 AList 下载，等同步真正跑完再开始，不依赖任何时间猜测：

- 整个串联过程同时持有同步与下载两把锁，期间定时的独立下载任务或网页手动触发都不会插进来
- 只影响**定时任务**；网页「任务」页手动点的「同步模式」与「AList下载」仍各自独立执行
- 开启后建议把 `alistCron` 留空；如需额外增加一次独立下载，仍可继续配置它
- 任务名会显示为「同步 + AList下载」，「任务」页可看到它的下次运行时间
- 未配置 `alistUrl` 时会记录一条告警并跳过下载（同步结果不受影响）；下载失败也只记录错误，不会让已经成功的同步算作失败

### 失效链接清理

`pruneDeadShares` 开启后，任务执行完会从配置里移除**确定失效**的分享链接。临时网络故障、限流、提取码错误都不会误删；默认关闭，仅报告。

## 试运行（预览）

在真正动网盘之前先看清楚会发生什么：

```bash
npm run sync-dry              # 等价于 node src/index.js --dry-run
```

网页上则在「任务」页的「手动触发」里点「试运行同步」，输出照样写进日志（「日志」页可看）。

试运行**照常执行读取类操作**：校验 Cookie、遍历分享、按时间窗口 / 体积 / 数量筛选、与目标文件夹比对去重，并逐条列出「会转存哪些文件」。但**不执行任何写入**：

- 不创建目标文件夹（目录不存在时按「新建空目录」计算，因此没有文件会被判定为已存在）
- 不转存文件、不真正重命名（清单里给的是**加前缀之后**的名字，见下）
- 不清理过期文件、不把失效链接写回配置

### 输出只有文件清单

试运行只回答「会转存哪些文件」，因此进度类日志（步骤编号、token、目录解析、筛选计数等）**全部静音**；**报错照常输出**（走 ERROR 通道，可在「日志」页按 ERROR 过滤）。

清单里列出的是**加完影视名称前缀之后的最终文件名**，与正式运行结束时「成功转存的文件」一致；分享里的文件本来就带这个前缀时不会重复叠加（同 [去重与重命名](#去重与重命名)），没设影视名称的分享自然还是原始文件名。整块清单用 `═` 分隔线围起来 —— 前后紧挨着的都是其它时间点的日志（手动触发、任务完成等），不隔开就分不清清单从哪开始、到哪结束。输出形如：

```
══════════════════════════════════════════════════
待转存文件列表:
  - 遮天-182 4K.mp4  (更新于: 2026/9/22 19:01:47)
  - 遮天-183 4K.mp4  (更新于: 2026/9/22 19:01:47)

共 2 个文件会被转存（试运行，未做任何写入）
══════════════════════════════════════════════════
```

没有要转存的文件时：

```
══════════════════════════════════════════════════
待转存文件列表:
  （没有需要转存的文件）

共 0 个文件会被转存（试运行，未做任何写入）
══════════════════════════════════════════════════
```

配了多个分享时会按分享分组（用影视名称，没设名称则用分享 ID）—— 没设影视名称的分享只能靠分组看出文件来自哪里：

```
══════════════════════════════════════════════════
待转存文件列表:
[遮天]
  - 遮天-182 4K.mp4  (更新于: 2026/9/22 19:01:47)
[a1b2c3d4e5f6]
  - 电影.2024.1080p.mkv  (更新于: 2026/9/21 15:50:05)

共 2 个文件会被转存（试运行，未做任何写入）
══════════════════════════════════════════════════
```

静音只作用于本次试运行的异步上下文（`AsyncLocalStorage`），因此同一时间在跑的其它任务（sync 与 alist 用的是两把锁，可以并发）的日志不会受影响。

`--dry-run` 目前**只支持同步模式**：用在 download / alist / schedule / web 上会直接报错退出。这是有意的 —— 若静默忽略该参数，用户会以为「已经预演过了」，实际却真的执行了。

## 网页界面

- **Cookie 不回显**：`GET /api/config` 只返回形如 `sk-a****wxyz` 的掩码值，完整 Cookie 永不下发到浏览器；保存时若回传掩码值，后端会保留磁盘上的原值，不会把掩码写进配置
- **Token 可热更新**：在网页里修改 `webToken` 后立即生效，旧 Token 立刻失效，**不需要重启**（已登录的会话仍然有效）
- **默认监听 `0.0.0.0`**：局域网可访问（方便手机/其他设备打开）。只想本机使用就把 `webHost` 设为 `127.0.0.1`。注意 Docker 的 `ports` 映射会绕过这一层保护，**鉴权是唯一防线**，请务必使用足够复杂的 `webToken`
- **任务互斥**：同步与 AList 任务同一时间只允许一个运行，定时触发与网页手动触发共用同一把锁，重复触发会返回「已有任务正在运行中」
- **启动任务**：进程启动后会先跑一次同步和 AList 下载，设置为 `"runOnStartup": false` 可关闭
- **界面上有意不出现的字段**：全局 `tip`、`password`（改为逐分享维护）与 `targetDirFid`（高级选项）。它们仍会照常生效，保存配置时原样保留，不会被清掉

## 日志

所有运行日志写入项目根目录的 `sync.log`，包含时间戳和日志级别。日志按时间**顺序追加**（旧 → 新），自动保留最近 7 天。

网页「日志」页有四种视图，默认是**汇总**：

| 视图 | 内容 |
| --- | --- |
| **汇总**（默认） | 只留总的转存结果汇总（`=== 全部转存结果汇总 ===`、`共处理 N 个分享，成功: X 个，失败: Y 个`、成功 / 失败文件清单；单分享时是 `同步完成: 成功 X 失败 Y`），外加任务边界与 `═…═` 分隔线、下载与清理结果、试运行清单，以及**全部报错与警告**（含 INFO 级别里的 `✗`、`⚠`）。每个分享自己的处理过程整段不显示 |
| **分享明细** | 在汇总的基础上补上每个分享的筛选漏斗（找到 N 个 / 时间窗口内 N 个 / 候选 N 个 / 跳过 N 个 / 需要转存 N 个），用来回答「这个文件为什么没转存」 |
| **全部日志** | 原样输出，步骤进度、逐个文件的筛选与重命名、去重提示都在这里 |
| **登录日志** | 网页登录成功 / 失败、退出登录，以及夸克登录态校验（`0. 验证登录状态...`、`Cookie 无效或已过期`） |

判定以「记录」为单位：一条记录 = 一行带时间戳的日志 + 其后的续行，所以多行消息（例如只有前缀行的 `程序异常: …`）不会被截成半截；「行数」上限同样按整条记录取，宁可少给一行也不切开一条记录。

「汇总」要整段丢掉某个分享的日志，而「这条属于哪个分享」不在单条记录里，因此会先按顺序扫一遍分段落：分享段从 `处理第 N/M 个分享` 或 `分享 ID:` 开始（单分享时没有前者），到总结果为止；`═…═` 分隔线跟着它**后面**那条记录走，所以分享前的线随分享一起折叠，总结果前的那条保留。段落是在「级别 / 关键字」过滤之前算的，只按 ERROR 过滤也不会打乱判断。

两个汇总类视图都只折叠**明细**，报错一条不少；被折叠的行数会显示在日志框下方（「已折叠 N 行明细」），切到「全部日志」即可展开。新增日志时若属于关键结论，需要把特征补进 `src/index.js` 的 `SUMMARY_KEEP`；拿不准就别加 —— 汇总里多一行只是啰嗦，少一条结论才是问题。

登录日志带来源 IP（`网页登录成功 (来自 192.168.1.5)`），反向代理下取 `X-Forwarded-For` 的第一段；该头部由客户端可控，因此只保留 `0-9a-fA-F:.` 字符再写进日志。退出登录只在真的销毁了一个会话时记录。

`web` 模式启动时会打印当前版本，例如 `=== 夸克网盘定时任务 v1.6.1 ===` —— 容器里 `docker logs quark-sync | head -3` 就能确认跑的是哪个版本；网页「管理面板」页头也会显示同样的版本号。

消息首尾的空行只在终端里起分隔作用，写进文件前会被去掉（`log('')` 这种纯分隔不落盘），所以文件里每条记录的首行都带时间戳和级别，`═` 分隔线也是整行带时间戳的 —— 读日志时不会看到「只有时间戳、没有内容」的空记录。

网页界面从文件尾部读取，因此日志文件很大时也只读取需要的部分。若检测到旧版本留下的倒序日志（最新在前），会在首次写入时自动迁移为顺序。

## 工作流程

### 同步模式

1. 加载 `config.json` 并验证 Cookie 有效性
2. 遍历 `shareUrls` 中的每个分享链接，获取目录树（失效链接自动跳过）
3. 筛选出多久内更新（`hours`）范围内更新过的文件（可每个链接单独配置）
4. 按 `minFileSizeMB` 过滤掉过小的文件（可每个链接单独配置）
5. 按 `maxFilesPerShare` 限制数量，只保留更新时间最新的 N 条（可每个链接单独配置）
6. 与目标文件夹已有文件比对去重（按文件名 + 文件大小）
7. 分批（每批 20 个）将新文件转存到目标文件夹
8. 若配置了 `tip` 前缀，自动重命名转存后的文件

### 下载模式

1. 列出网盘目标文件夹中的所有文件
2. 从 `.downloaded.json` 加载已下载记录，跳过已完成的文件（按文件名 + 大小匹配）
3. 分批（每批 10 个）获取下载地址，并行下载（并发 3 个）
4. 每个文件下载成功后立即写入 `.downloaded.json`，即使中途中断也不会重复下载
5. 若启用 `deleteAfterDownload`，下载后从网盘删除文件

## 发布镜像

发布流程：**先改 `package.json` 的版本号并提交，再发布**，这样镜像内记录的版本与 tag 才一致。

### GitHub Actions（推荐）

不需要本地装 Docker，`linux/amd64` 与 `linux/arm64` 都在 runner 上构建。两种触发方式：

1. 仓库页 → **Actions → Publish Docker image → Run workflow**
2. 打 tag：`git tag v<版本号> && git push origin v<版本号>`（tag 必须与 `package.json` 的版本一致，否则任务失败）

首次使用前要配置两个密钥（**Settings → Secrets and variables → Actions → New repository secret**）：

| Secret | 值 |
| --- | --- |
| `DOCKERHUB_USERNAME` | Docker Hub 用户名，即 `hsiangleev` |
| `DOCKERHUB_TOKEN` | Docker Hub 的 Access Token（**不是**登录密码） |

Token 的获取路径：Docker Hub → 右上角头像 → **Account settings** → **Personal access tokens** → **Generate new token**，权限选 **Read & Write**；生成后只显示一次。

几点说明：

- 工作流直接调用仓库里的 `scripts/docker-build.mjs`，所以 tag 规则、平台列表与本地 `npm run docker:build` 完全一致，不会出现两套规则
- 有意**不做**成「push 到 main 就自动发布」：版本 tag 一旦发布就应当是不可变的，否则一次依赖升级（同样会改 `package.json`）就可能悄悄覆盖已发布的镜像
- 若该版本已发布过，任务会直接失败并提示；确实要覆盖时，手动运行并勾选 `overwrite`
- 公开仓库的 Actions 分钟数免费；私有仓库会消耗每月额度

### 本地构建

`npm run docker:build` 会读取 `package.json` 的 `version`，同时打上 `latest` 与 `<版本号>` 这样的版本 tag；发布前若工作区有未提交改动、或 HEAD 中的版本与工作区不一致，会给出警告。
